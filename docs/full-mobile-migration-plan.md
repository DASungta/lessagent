日期：2026-11-17。状态：R0 静态盘点与基线归档已实施；原版真实页面、动态入口及关键原生/云链路验收仍有阻塞。R1.1–R1.6 的客户端功能已实施，并在专用 Mate 60 Pro 完成真实升级、多环境/多路径、扫码/深链、锁屏存储、有效公开 HTTPS 配对和 C05 批准/拒绝/撤销；原版 B01 已在 Android 模拟器取得视觉/交互证据（原版二维码识别受合成相机限制），IPv6/Tailnet 实网组合仍未闭合。R2 客户端链路已实现并通过本地契约测试与签名构建，但真实 Clerk/中继、合法鸿蒙 OAuth 客户端及设备 DPoP 执行仍阻塞，见 [R2 进展](r2-progress.md)。具体产物和证据见 [R0 交付记录](r0-delivery.md) 与 [R2 evidence](evidence/r2/README.md)。下文规划与历史边界保留。

## 1. 对齐对象与完成定义

- 对齐用户 fork `DASungta/t3code` 的 `apps/mobile`，固定源码基线 `ad1b1365999c92c3fc7a054e7f3af84623f74fee`。已在本机 `/tmp/t3code-harmony-upstream` 核实 SHA；该临时目录不是长期依赖，实施前保留可复现的源码基线。
- 迁移原版移动端在对应配置、账号权限和服务端能力下提供的全部产品能力。包括可选开启的 T3 Connect；不能因本机默认未配置而从范围删除。
- 保持原版页面层级、入口位置、操作顺序和状态反馈；用 ArkUI 原生导航、菜单、弹层、列表、输入和系统能力翻译，不重新发明产品流程，不用 WebView 承载客户端页面。
- 平台专有机制保留同等用户结果，通过鸿蒙能力实现。无法等价时单列差异和阻塞，不用空按钮或静态演示冒充迁移完成。
- 原版 mobile 的 `src/connection/platform.ts` 明确对 SSH 返回 unsupported（仅桌面端可用）。SSH 不属于本轮移动端对齐范围；不是遗漏，也不把它伪装成可用入口。
- 源码存在不等于对所有账号可用。实验开关、服务端能力、权限和云配置的启用条件必须随功能迁移。

每项功能只有在“入口一致、真实请求与状态一致、正常与异常路径验证、真机交互通过、有证据”后才标为完成。源码测试、模拟响应、离线样例与真实业务证据分开记录。

## 2. 当前基线与不能沿用的结论

已有：单服务器 Bearer 直连、项目/模型选择、会话创建和订阅、基础消息/工具/代码展示、审批与输入、停止、单文件附件、安全存储及恢复保护。构建和本地测试已有基础，历史真机业务验证范围以阶段文档为准。

尚不是原版完整实现：仅一个连接；二维码/配对链接、局域网地址兼容、T3 Connect、多环境未迁移；项目/会话操作和完整输入能力不齐；文件/Diff/终端/PR/预览、系统集成和大量设置未实现。

当前 UI 只能作为待校对的原生实现。即使外观近似，也不能继续认定流程等价：例如现有“选项目模型后创建空会话”的表单需与原版草稿任务创建流程重新逐项对齐。

## 4. 优先实施的连接模块

### R1：先把原版配对和多环境完整打通

1. **环境目录与数据隔离**：把单例连接状态拆为环境目录、按环境持有的连接会话和当前选择。多环境可以独立连接/断开/重连，不能只在一个地址字段上覆盖。环境、项目、会话统一使用带环境范围的标识。
2. **兼容原有数据**：现有安全凭据和恢复记录迁入环境范围；先写入并校验，再切换引用，失败保留旧数据。未知提交标记必须随原环境/会话保留。目录与非敏感配置和凭据分开存储；不能把多环境目录硬塞进目前 1024 字节的安全记录。
3. **配对入口**：按原版“扫码 / 手动地址与配对码”组织添加环境页面。统一解析配对 URL、原版托管配对链接和 `t3code:` 包装链接；扫码只填入经过校验的目标，明确用户连接动作，不能打开任意扫描 URL 或绕过校验。
4. **地址与传输**：对齐局域网、tailnet 和公网直连语义。明确原版允许的 HTTP 使用场景，并评估鸿蒙网络限制；不得为了支持局域网关闭 TLS 验证或允许鉴权信息随重定向泄漏。二维码/地址解析、协议鉴权和传输策略分别测试。
5. **原生系统接入**：相机/扫码权限及拒绝处理、应用链接唤起和冷启动暂存；扫描后停止重复识别。优先验证系统能力是否满足，不能假定 Expo 模块可直接使用。
6. **环境管理**：原版已有/可用环境分组、连接状态、启用/禁用、重试、移除和诊断信息。保存原版的错误、过期和需重新配对提示。

R1 的完成条件：两台独立测试环境，从扫码与手动入口分别建立连接；切换、同时存在、断开一个、重启和删除一个均不影响另一个的凭据、会话、草稿、附件和恢复记录。旧版本升级数据验证通过。

### R2：T3 Connect 是完整链路，不是第三个输入框

- 核实上游公开配置、身份提供方、鸿蒙客户端注册/回调方式、合法账号及测试环境是否可用；这些是外部依赖，不能复制其他平台私密凭据或假定其客户端身份可复用。
- 按实际认证协议完成登录、回调校验、会话恢复、注销和账号隔离；仅在确有相应协议要求时实现 PKCE 等机制，不猜测服务契约。
- 对齐 DPoP P-256/ES256 密钥、proof、nonce/时间偏差、令牌绑定和续期；用上游向量核对签名格式，并在鸿蒙安全存储/密码能力上验证。密钥可用性、锁屏限制与迁移失败必须处理。
- 迁移账号环境发现、可用/已连接环境、设备批准/拒绝/撤销、连接诊断、中继连接和服务能力判断。
- 按原版契约处理直连/中继策略，不臆造“失败就任意回退”。断线恢复期间不自动重发修改请求。

R2 的完成条件：跨网络、确实通过中继完成创建会话→发送→回复→审批的闭环；同时验证续期、失效、撤销、账号切换及直接连接与中继环境并存。缺少可用账号/回调或云配置时记为阻塞，R1 完成不能算连接模块完整完成。

**R2 实施状态（2026-11-17）**：公开配置门控、Clerk OAuth/PKCE 会话与回调、CryptoFramework DPoP、账号/令牌缓存隔离、环境发现、link challenge/link/unlink、设备批准/拒绝/撤销、relay status/connect/ticket、环境 DPoP exchange、直连云同 ID 共存及端点轮换恢复已落地；153 项宿主测试和普通签名构建通过。默认公开配置为空，没有真实 Clerk 账号、鸿蒙 OAuth client、已 link 环境或真实 relay；DPoP 诊断 HAP 已构建但未在设备执行。因此 C06–C10 均为**已实现未验收**，不能宣布 R2 完成。按用户 2026-11-17 指令，R3 未等待 R2 真实云验收先行开发，R2 状态保持不变。

**R3 实施状态（2026-11-17）**：项目来源/分组/概览、会话搜索/过滤/固定/暂缓/Settle/归档/重命名/删除/撤销、No project 和归档页已实现；173 项宿主测试与最终签名构建通过。专用 Mate60Pro 已对隔离 T3 0.1.9 服务完成新建/本地目录/克隆成功失败重试取消、项目概览、会话 Settle/撤销/归档/恢复/暂缓/排序及项目选择衔接的真实回读。原版逐页视觉、拖拽排序、运行中归档限制、严格权限矩阵和 provider 真实副作用仍未验收，详见 [R3 进展](r3-progress.md)。

## 5. 实现结构与复用原则

- 延续 ArkTS + ArkUI；服务端 Agent 和现有业务协议保持原职责，不为 UI 简化而改变服务端语义。
- 原版 contracts、纯解析/状态归约逻辑和测试向量逐项评估可移植性；ArkTS 不兼容部分做小范围适配，不盲目导入整套 React/Expo/Effect。
- 当前 `T3Client` 承担网络、鉴权、状态和单例恢复，按 R1 实际需要拆分环境目录与连接实例；不提前建设通用插件框架。
- `SessionStore` 负责环境范围的凭据/密钥/恢复记录；`AttachmentPicker` 使用明确环境及会话范围；页面仅绑定已选择的环境状态。
- 按原版路由拆分页面和职责，`Index.ets` 逐步成为入口，避免继续把全部新功能堆在一个页面。
- 终端、代码/Diff、设备画面和语音分别做鸿蒙原生能力原型；必要的原生桥接单独评估，不承诺 ArkTS 文本控件能替代终端或视频渲染。
- 浏览器预览功能与“用 WebView 替代客户端 UI”严格区分。先核对原版远程预览协议，再决定原生画面/输入实现；任何确有网页内容需求的嵌入另行明确技术边界。

## 6. 交互和视觉验收规则

R0 为原版核心路径建立屏幕与操作基线：无环境→添加环境→扫码/手动/T3 Connect；列表→新任务→模型和上下文选择→发送；运行→审批/回答→完成；文件/审阅/终端；设置。

每个页面写明：原版入口、跳转/返回顺序、工具栏位置、手势、焦点/键盘、加载/空/错误/禁用/离线状态和对应 ArkUI 组件。优先沿用原版布局/主题/层级，仅为鸿蒙系统规范作必要适配。

每个批次按相同内容、设备尺寸和字体档位比较原版与鸿蒙真实页面。源码推断和临时样例只做辅助，不能再把“看起来类似”的截图当成交互等价证明。最大字体、深浅色、读屏和键盘验收贯穿各批次，不全部推迟到最后。

## 7. 测试、交付和推进顺序

执行顺序：**R0 → R1 → R2 → R3 → R4 → R5 → R6 → R7 → R8**。R0 同时先验证云登录/DPoP、原生终端、远程预览和通知的关键外部条件，避免直到后期才发现路线不可行；这不代表提前宣称相关功能已实现。

每批交付：

1. 功能矩阵更新，状态仅用待实施、实施中、已实现未验收、已验收、阻塞。
2. 实际代码和可安装签名 HAP；无新增无效入口，无业务静默降级。
3. 相关协议/状态/存储迁移测试、构建与静态检查；已有检查保持通过。
4. 真机正常与异常闭环记录，涉及服务写入时回读结果；真实凭据和私密内容不进入证据文件。
5. 未通过项、回退方法和影响说明；保存与历史结果的边界。

当前目录没有 Git：保护已有文件并保存每批变更清单和必要备份；不擅自初始化仓库、提交、发布或重启现有服务。测试使用独立环境/会话，避免影响真实工作。

不在当前粗盘点基础上给出虚假的总工期。R0 完成后按实际路由数量、系统桥接原型和外部依赖分别估算；R1/R2 是第一组实施目标，但不是整个迁移项目的最终范围。
