## 1. 目标与项目边界

使用 ArkTS + ArkUI 构建鸿蒙原生客户端，优先手机，后续适配平板和折叠屏。连接自己的电脑或服务器，复用现有 T3 Code 服务端能力。

本项目位于独立目录 `t3code-harmony`。此前提出的 `apps/harmony` 是放入 T3 monorepo 的组织建议；目前采用独立工作目录，后续是否合并回 fork 单独决定，不作为开发前置条件。

原生体验范围包括导航、页面、聊天、Markdown、代码块、Diff、输入和状态管理。完整终端独立验证，不以普通日志列表或 WebView 冒充完成。

第一目标是可日常使用的远程编程客户端，不要求首版完整复刻现有 mobile 的所有高级功能。

主要参考路径：

- `packages/client-runtime/src/authorization/remote.ts`：HTTP 鉴权与 WebSocket ticket 获取。
- `packages/client-runtime/src/connection/resolver.ts`：直连、SSH、T3 Connect 等连接路径。
- `packages/client-runtime/src/connection/compatibility.ts`：协议兼容性与能力声明。
- `packages/contracts/src/orchestrationV2.ts`：快照、序列号、命令与会话事件契约。

现有客户端存在 Expo 依赖和自定义原生模块，不能通过切换编译目标直接得到 ArkUI 应用。共享 TypeScript 代码逐项评估；不假设整个 `client-runtime` 或 Effect 运行时可直接导入 ArkTS。

## 3. 技术架构

### 客户端

- ArkUI：页面、导航、消息列表、Markdown、代码与 Diff 展示。
- ArkTS：协议编解码、状态更新、连接管理、缓存和生命周期。
- 系统能力：网络、安全存储、文件选择、剪贴板、分享。
- 开发工具：DevEco Studio；最低系统/API 版本和 SDK 在目标设备确认后锁定。

初期使用单一应用模块，按职责分目录，不预先拆分多个共享库或引入额外 JS 运行时。

拟定结构，实际由 DevEco 工程生成后落实：

```text
t3code-harmony/
  README.md
  docs/
    development-plan.md
  entry/src/main/ets/
    pages/
    components/
    state/
    protocol/
    services/
    storage/
```

### 服务端

沿用 T3 Code 的 Agent 执行、工作区管理、命令执行和会话持久化能力。第一阶段以兼容已有协议、无需修改服务端为验收目标。

原生直连为主方案，不预先增加协议转换网关。只有原型发现明确阻碍，才重新评估网关及其部署、鉴权、维护成本。

## 4. 协议接入方案

第一优先级是打通协议，不先大规模铺设页面。

### 鉴权与连接

1. 按现有协议获取和校验环境信息、服务器身份及版本。
2. 使用合法凭据完成 HTTP 鉴权与 WebSocket ticket 获取。
3. 建立 WebSocket 连接，声明实际支持的协议与客户端能力。
4. 拉取初始状态并建立所需订阅。

首版采用服务端现有的直连鉴权流程，凭据获取和配对入口需在原型阶段核实。T3 Connect 登录、中继、DPoP 和 SSH 自动启动远端服务后续独立实现。

### RPC 与事件

- 请求编号、响应匹配、超时和错误映射。
- 流式订阅、结束、取消、心跳，以及协议实际要求的确认机制。
- 实际使用的帧分片与重组能力；先核实协商条件，不自行假设格式。
- 快照与增量事件合并、序列号去重和断线恢复。
- 无法增量恢复时重新获取快照。
- 严格校验外部输入；未知消息和版本不兼容必须给出可诊断结果。

按首版需要实现协议子集，不重写完整 Effect 框架。通过真实协议样例和集成测试证明兼容性。

### 防止重复执行

界面区分正在提交、已确认、执行中、完成、失败和结果未知。

网络中断后先核对服务端状态。核实 `commandId` 的幂等和去重语义之前，不自动重发可能修改代码或执行命令的请求。只对明确安全的读取和订阅实施自动重试。

### 5.3 各阶段任务明细

#### 阶段一：工程与协议原型

工作：

- 确认真机型号、系统版本、SDK、签名和安装方式。
- 建立可构建、可安装的 HAP 工程。
- 固定联调服务端版本，核实凭据获取入口。
- 实现鉴权、ticket、RPC、流式消息与基本错误处理。
- 建立脱敏协议样例和编解码测试。

验收：

- 鸿蒙真机连接现有服务，创建会话、发送指令并收到完整回复。
- 不需要修改服务端协议。
- 错误凭据、协议不兼容和断线均能明确呈现。

这是第一个交付节点。通过后再确定后续详细排期。

#### 阶段二：核心客户端

工作：

- 服务器配置、安全保存凭据与连接状态。
- 项目、会话列表，新建会话和模型选择。
- 历史记录、输入草稿、流式回复和工具执行状态。
- 权限审批、用户输入请求、敏感输入和停止任务。
- 基础 Markdown、代码块复制及安全重试入口。

验收：

- 完成一次提出代码修改、审批工具执行、查看结果、继续追问的真实流程。
- 敏感输入不进入普通日志或不必要的持久化缓存。

#### 阶段三：恢复与原生体验

工作：

- 前后台切换、Wi-Fi/蜂窝切换、服务端重启后的恢复。
- 事件去重、补齐和快照回退。
- 长会话懒加载、局部更新、流式更新合并与滚动位置保持。
- 键盘避让、文本选择、深浅色、大字体和无障碍。
- 附件选择、上传及失败恢复。

验收：

- 锁屏、切网、进程退出后再次进入，状态与服务端一致。
- 不重复执行已提交任务，不重复显示已处理事件。
- 长会话和快速流式输出下，输入与滚动保持可用。

阶段二、三完成后形成第二个交付节点：可日常使用的原生聊天客户端。

#### 阶段四：代码审阅

工作：

- 原生文件列表、源码查看、语法高亮。
- 手机单栏增删行 Diff，大文件分段加载。
- 工具输出展开、搜索和复制。
- 平板、折叠屏双栏布局。

验收：

- 能在手机上读懂一次真实代码修改。
- 大型代码块和 Diff 不阻塞输入及滚动。

#### 阶段五：高级能力与发布

分别立项验证：

- 完整交互终端。
- T3 Connect 登录、中继、DPoP 和令牌续期。
- SSH 连接与远端服务启动。
- 后台完成推送、语音和系统分享入口。
- 签名发布、升级安装、缓存迁移与兼容性回归。

这些能力不作为核心客户端首个交付的前置条件。公开发布前再核实许可证、品牌使用和所依赖云服务的接入条件。

## 6. 原生渲染与系统行为

### Markdown、代码和 Diff

- 解析与 ArkUI 渲染分离。
- 先支持段落、列表、引用、链接和代码块，再补充表格等格式。
- 复用解析库前验证 ArkTS 兼容性和许可证，避免自行实现完整 Markdown 标准。
- 流式输入只更新变化区域，已完成消息尽量保持稳定。
- 使用与目标 SDK 匹配的列表懒加载和组件复用机制。
- 高亮按可见内容、文件大小和语言能力限制工作量；超大内容允许明确降级为纯文本。

### 完整终端

终端需独立验证控制序列、光标、滚动区、颜色、中文字符宽度、输入法、按键映射、窗口尺寸同步和选择复制。原生日志查看只作为单独能力，不计入完整终端验收。

### 生命周期

以服务端继续执行、客户端恢复后同步为设计基础，不依赖手机后台永久保持 WebSocket。根据 UIAbility 生命周期保存必要状态、清理无用订阅并恢复连接。后台完成通知需要独立的推送链路验证。

### 存储与安全

- 服务器配置、草稿、缓存与凭据分别管理。
- 凭据使用系统安全存储；Asset Store 的大小限制需要检查，超长凭据使用合适的加密方案。
- 日志不记录 token、ticket、带鉴权参数的完整 URL 或敏感输入。
- 保持 TLS 证书校验，不以跳过校验解决连接失败。
- 缓存按服务器和会话隔离，切换服务器不能混用数据。
- 退出或删除服务器时明确处理凭据及缓存；客户端缓存不替代服务端会话记录。

## 7. 测试与验收策略

### 协议测试

保存脱敏样例，覆盖请求、响应、流式结束、取消、错误、乱序或重复事件、重连及快照回退。样例不能包含真实凭据或业务私密内容。

### 服务端集成测试

同一测试任务分别由现有客户端和鸿蒙客户端操作，核对最终状态。验证权限拒绝、停止任务、提交结果未知时的恢复，不仅检查 WebSocket 是否连接成功。

### 真机测试

覆盖长会话、快速输出、大 Diff、附件、切网、锁屏、进程退出、服务端重启和凭据失效。记录设备、系统、客户端和服务端版本；性能阈值依据目标设备基准测试确定。

### 持续验证

每阶段执行工程构建、静态检查、相关单元测试和实际业务链路验收。CI 的 DevEco/HarmonyOS 构建环境、签名材料管理及真机验证方式在工程建立后落实。

## 8. 上游维护与排期原则

- 记录首版支持的服务端版本和协议范围，不承诺自动兼容所有上游版本。
- 升级上游时优先审查 contracts、鉴权和 RPC 变化。
- 核心协议样例及联调回归通过后再扩大兼容范围。
- 不兼容时给出明确升级或降级提示。
- 第一阶段完成后，以真实协议工作量、ArkTS 限制和设备性能重新估算工期。
- 完整终端、T3 Connect、SSH 和推送单独估算，不混入聊天客户端的交付承诺。
